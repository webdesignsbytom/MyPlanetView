Internal reference — server/src/services/s3

How media moves through this backend

One S3-compatible bucket, four routes, and a tracking table called MediaItem. This page explains the vocabulary, the four routes byte-for-byte, and the reasoning behind why uploads never pass through this server at all.

Glossary

Terms used throughout this document and the codebase, in plain language.

S3
Simple Storage Service. Amazon's original object-storage product; the API shape ("buckets" containing "objects", addressed by a "key") is now a de-facto standard other providers copy. This project's bucket is hosted on Hetzner, not AWS, but speaks the identical S3 API.
Bucket
A named storage container at the S3 provider. Everything this app uploads lives in one of two buckets — see public vs. private.
Object / Key
A "key" is an object's full path inside a bucket, e.g. testing/avatars/user123/2026/07/pic_a1b2.png — there are no real folders in S3, just keys that look like paths.
Presigned URL
A normal S3 URL with a cryptographic signature and expiry baked into its query string, generated using this server's real credentials, then handed to someone who doesn't have those credentials. S3 verifies the signature itself — the server isn't involved once the URL is issued.
PUT / GET / DELETE
HTTP methods. PUT uploads a file to an exact key. GET downloads one. DELETE removes one. A presigned URL authorizes exactly one of these, for one exact key, until it expires.
MIME type
Also "content type" — a short label like image/png or application/pdf describing what kind of bytes a file contains. Declared by the uploader; used here to decide which folder accepts it and how big it's allowed to be.
TTL
Time To Live — how many seconds a presigned URL stays valid before S3 starts rejecting it.
CORS
Cross-Origin Resource Sharing. The browser-enforced rule that a page loaded from one origin (e.g. localhost:5173) can't call an API on a different origin (the bucket) unless that origin explicitly allows it. Configured via setBucketCors.js.
CDN
Content Delivery Network. A caching layer often placed in front of a public bucket so images load from a server near the visitor, instead of the bucket's home region every time.

Core concepts

Public vs. private buckets

This isn't a spectrum — it's a hard switch at the bucket level, called Block Public Access.

Public

Anyone with the URL can GET the object — no signature, no login, forever. Paste it straight into a browser tab and it loads.

Use for: avatars, blog images, gallery photos — anything meant to render on a page anyone can visit.

Private

Block Public Access is switched on for the whole bucket. A raw URL with no signature is refused outright — even by accident. Every read needs a fresh, short-lived presigned GET.

Use for: ID documents, private attachments, anything access-controlled.

Current state of this project

Only one bucket is provisioned right now, and it's public. The contact resource (see registry below) needs private-style access control, so it's simulated at the application level instead: the object is technically fetchable by anyone who has the exact key, but that key is never handed to anyone except an authenticated admin/dev. That's a real, working control — just not the hard guarantee a second, real private bucket would give. Flipping one config value (visibility: 'private') is all that changes when that bucket exists.

Presigned URLs, and why bytes never touch this server

A naive upload design proxies the file through Express — multer, req.file, re-upload to S3. That works, but doubles bandwidth and ties up server memory on every upload. Presigning flips the sequence:

The server's only job is deciding whether the upload should happen — auth, resource type, MIME allowlist. It never sees the file's bytes.

The MediaItem ledger

One row is written to the MediaItem table the moment a key is presigned — regardless of which feature asked for it. It's the single place that answers "what resource is this key for, who owns it, and how big is it?" without every feature reinventing that bookkeeping.

ColumnMeaning
keyThe S3 object key. Unique.
resourceWhich registry entry it belongs to — avatar, blog, guestBook, contact.
kindIMAGE / VIDEO / FILE, derived from the declared MIME type.
visibilityPUBLIC or PRIVATE, mirrors the resource's bucket.
bytesReal size, filled in by confirm-upload — not trusted from the client.
originalFilenameWhat the uploader called it, for admin UIs and downloads.
ownerIdWho uploaded it — null for anonymous uploads (e.g. a visitor's contact-form image).

Resource registry

Every upload is presigned against one named "resource" — this is the single source of truth for what folder it lands in, who may upload there, what file types are accepted, and how big they're allowed to be. Anatomy of a key

Every uploaded object's key is built the same way, regardless of resource:

testingnamespace/ avatarsresource/ u_812aowner / anon/ 2026year/ 07month/ pic_x9q2name + random. pngextension

namespace exists because this bucket is shared across multiple client projects — it's one constant (BucketNamespace) that keeps every project's keys from colliding in the same bucket.

The four routes

Everything mounts under /media-services. All four share the same resource registry above — nothing about "which bucket" or "what's allowed" is route-specific.

POST /media-services/presign-url
rate-limited · 20 / 15 min auth optional

Asks for permission to upload, and gets back a signed PUT URL if granted. Whether a session is required depends entirely on the resource being asked for (an anonymous visitor can request one for contact; only a logged-in user can for avatar) — so this one route can't blanket-require login, it identifies the caller if a session exists and lets the registry decide.

Request body

{
  "resource": "avatar",
  "filename": "profile.png",
  "contentType": "image/png"
}

Response — 200

{
  "url": "https://bucket.host/…&X-Amz-Signature=…",
  "key": "testing/avatars/u_812a/2026/07/profile_x9q2.png",
  "expiresIn": 600,
  "visibility": "public",
  "maxBytes": 5242880,
  "publicUrl": "https://bucket.host/testing/avatars/…",
  "method": "PUT",
  "headers": { "Content-Type": "image/png" }
}

publicUrl is only present for public resources — it's the finished, permanent URL to hand straight to an <img> tag once the upload succeeds, with no second lookup needed.

POST /media-services/confirm-upload

Called by the client right after its direct-to-S3 PUT finishes. A presigned PUT can't cap file size up front — that needs a different mechanism (presigned POST with a size-range policy). Instead, this route asks S3 itself how big the object actually turned out to be, and rejects anything over the limit for its kind — deleting it immediately rather than leaving an oversized file sitting in the bucket.

{ "error": "File too large (7340032 bytes) — max for image is 5242880 bytes." }

auth required permission-gated

Mints a short-lived signed GET URL. Public resources don't need this at all — build publicUrl straight from the presign response instead. This route exists for resources flagged restrictedView (today: just contact) — a session is required, and the caller must be ADMIN or DEVELOPER.

DELETE /media-services/delete-object?key=…
auth required ownership-gated

Removes the object from S3 and drops its MediaItem row. Allowed only if the caller owns it (MediaItem.ownerId matches their session), or is ADMIN/DEVELOPER. An object with no owner at all — an anonymous contact-form upload — can only ever be deleted by admin/dev, since there's no account to match.

Response — 204

Empty body, deletion confirmed.

Response — 403

{ "error": "Not authorized to delete this object." }

Step 3 is where controllers/contact.js checks the submitted imageKey actually has the contact/ prefix before trusting it — a client can't attach a key from a different resource. Nothing in the response to the visitor ever includes a viewable link; only the admin-only get-all-contact-forms endpoint returns the raw key, and only that can be exchanged for a viewable URL.

Known limitation

A presigned PUT trusts the declared Content-Type — S3 doesn't inspect the actual bytes. A renamed file could claim to be an image and pass the allowlist. Closing that gap for real needs a post-upload content inspection step; out of scope for this pass, worth knowing about.
