DummyFullstack site tests

Every part of the site, checked by hand: the public pages, accounts and the account page, the contact forms, reviews and the guest book, booking, the newsletter, the blog, the admin area, and the checks that cut across all of it. Each test says who to sign in as, what to do and what you should see, quoting the site's own words.

0Before you start

Run these from the repo root, in two terminals. A reseed puts every account and sample row back the way it is described, which matters because many tests change one (approve it, confirm it, delete it, deactivate it).

cd server
npx prisma db seed   # wipe every table and reseed
npm run dev          # the API on http://localhost:4000

cd client
npm run dev          # http://localhost:5173

npm run dev on the server restarts it whenever a file in src/ changes, and typing rs in its terminal restarts it by hand. Every restart clears the rate limits.

Two addresses. Page links go to the dev server, http://localhost:5173. Tests that need the built, pre-rendered site link to http://localhost:4173 instead: run npm run build, then npm run preview, in client/ first. There is no live site, because the template is never deployed. For a site built from it, set live in site-tests.json and rebuild this page: every page link then gets a live twin.

Password. Every seeded account signs in with 12345678. Register every throwaway account the tests ask for with the same password, so the line above each test holds.

Real inboxes. The three seeded accounts use real gmail.com addresses that belong to strangers. Never send anything to them: no password reset, no email change confirmation, no booking or newsletter in their name. Wherever a test checks an email, use an address you can read. The sample rows (bookings, subscribers, guest book) use example.com addresses, which never deliver anywhere.

Email. Account, contact and booking mail goes out over SMTP, so EMAIL_HOST, EMAIL_PORT and the mailbox settings must be set in the server env (the server will not start without the first two). The newsletter goes through Resend and needs RESEND_API_KEY and an EMAIL_FROM on a domain verified in Resend. Owner notifications go to CONTACT_ADMIN_RECIEVER_EMAIL and BOOKING_ADMIN_RECIEVER_EMAIL, called the owner inbox below. Every email a test expects is named by its subject line.

The browser and the API. FRONTEND_ORIGIN in the server env must list http://localhost:5173, and http://localhost:4173 for the build tests, or the API refuses every call. npm run env:check in server/ names anything missing without printing values.

Rate limits. Each public form allows 5 sends every 15 minutes, password reset and verification emails 5 every 15 minutes, and the whole API 300 requests every 15 minutes. The counts are kept in the server's memory, so restarting the server clears them.

Times. Bookings are in the site's time zone, SITE_TZ in the server env. An invalid name falls back to Europe/London.

Data. npx prisma studio in server/ shows every table. The audit log at /admin/events shows what each action recorded.

Part 8 · The newsletter

Everything a visitor does with the newsletter, signed out throughout: the sign-up form on /newsletter and in the home page box, the confirmation email and page, sending the link again, the unsubscribe page, and the one-click unsubscribe address that mail programs use. Every email goes through Resend, so the server needs RESEND_API_KEY and EMAIL_FROM on a domain verified in Resend; without them the forms still say they worked, but nothing arrives. Use three addresses you can read, called A, B and C below. Plus aliases of one Gmail address work (you+nl1@gmail.com, you+nl2@gmail.com, you+nl3@gmail.com). Rate limits: the sign-up form (one counter shared by /newsletter and the home page box), the confirmation page, the resend form and the unsubscribe page each allow 5 requests per 15 minutes from your connection. They are kept in memory, so restart the server (type rs in the npm run dev terminal) where a test says so, or whenever a red message starting Too many requests appears. The curl commands are for Windows PowerShell: type curl.exe, not curl, which PowerShell turns into Invoke-WebRequest. In the Network tab each POST is preceded by an OPTIONS preflight: ignore it.
